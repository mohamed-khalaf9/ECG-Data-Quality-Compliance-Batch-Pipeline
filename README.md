## 1. Problem Statement

This project focuses on auditing the data quality of ECG machine measurements and their associated clinical notes.

The input data consists of two main datasets:
- **ECG machine measurements** (records per scan, including measurement values and machine identifier)
- **Waveform note links** (mapping between ECG scans and associated clinical notes)

A key data quality issue is that abnormal ECG scans may not always have corresponding clinical notes. This can lead to incomplete clinical interpretation and reduce trust in downstream data analysis.

To address this, the project builds a data pipeline that:
- Cleans and standardizes the raw datasets
- Identifies abnormal ECG scans based on measurement value ranges
- Detects scans that are missing associated clinical notes
- Aggregates results at the ECG machine level

### Outputs

The pipeline produces the following datasets:

- **Machine-level audit table(cart_metrics)**
  - `cart_id` (ECG machine)
  - `total_scans`
  - `abnormal_scans`
  - `abnormal_no_note_scans`
  - `compliance_ratio` (availability of notes for abnormal scans)

- **Abnormal No-Note Audit Table**
  - Detailed records of abnormal ECG scans that do not have associated clinical notes  
  - Follows the same structure as the machine measurements dataset

- **Cleaned Source Tables**
  - Cleaned ECG machine measurements dataset
  - Cleaned waveform note links dataset

These outputs enable monitoring of ECG data quality, highlight gaps in clinical documentation, and support building reliable downstream data pipelines.

## 2. Data Overview

This project is based on two main datasets that represent ECG machine measurements and their associated clinical notes.

---

### 2.1 ECG Machine Measurements

This table contains detailed measurements recorded by ECG machines for each scan.

Each record represents a single ECG study and includes:
- Patient identifier
- Study identifier
- Machine identifier (`cart_id`)
- Measurement values describing the ECG signal

#### Key Columns

| Column        | Description |
|--------------|------------|
| subject_id   | Unique identifier for the patient (shared across datasets) |
| study_id     | Unique identifier for the ECG study |
| cart_id      | Identifier of the ECG machine used |
| ecg_time     | Timestamp when the ECG was recorded |
| report_#     | Text-based report generated by the ECG machine |
| bandwidth    | Machine bandwidth setting |
| filtering    | Filter configuration used during recording |
| rr_interval  | Time between successive R-waves (ms) |
| p_onset / p_end | Start and end of P-wave (ms) |
| qrs_onset / qrs_end | Start and end of QRS complex (ms) |
| t_end        | End of T-wave (ms) |
| p_axis       | Electrical axis of P-wave (degrees) |
| qrs_axis     | Electrical axis of QRS complex (degrees) |
| t_axis       | Electrical axis of T-wave (degrees) |

This dataset is the primary source for detecting abnormal ECG scans based on measurement values.

---

### 2.2 Waveform Note Links

This table links ECG studies to their associated waveform files and clinical notes.

Each record represents a mapping between a study and its corresponding note.

#### Key Columns

| Column        | Description |
|--------------|------------|
| subject_id   | Patient identifier |
| study_id     | ECG study identifier |
| waveform_path| Path to the waveform signal file |
| note_id      | Identifier of the associated clinical note |
| note_seq     | Sequence number of the note |
| charttime    | Timestamp of the clinical note |

> **Important:** Only ECG scans that have associated clinical notes appear in this table.

---

### 2.3 Data Relationship

The two datasets are connected through:

- `subject_id`
- `study_id`

## 4. Data Profiling

Before designing the cleaning and transformation logic, a comprehensive data profiling phase was conducted on both datasets to understand data quality issues, schema consistency, and potential anomalies.

Due to dataset size, profiling was performed on **a representative sample of 50,000 rows per table**.

The profiling process was implemented using **Python (Pandas)** and focused on structural validation, statistical distribution checks, and data integrity rules.

---

### 4.1 Profiling Objectives

The profiling phase aimed to:
- Understand schema structure and data types
- Detect missing or malformed values
- Validate key identifiers and relationships
- Identify data quality issues impacting downstream processing
- **Guide the cleaning strategy design**

---

## 4.2 ECG Machine Measurements Profiling

### Key Observations

#### Data Completeness
- No missing values in primary identifiers (`subject_id`, `study_id`, `cart_id`)
- High completeness in measurement fields
- Gradual sparsity in report columns (`report_0` → `report_17`), indicating variable-length machine-generated reports

#### Data Consistency
- `study_id` is unique across records
- `subject_id` contains high duplication (multiple studies per patient), which is expected
- `cart_id` shows 150 unique ECG machines

#### Temporal Validity
- `ecg_time` successfully parsed with no missing timestamps
- Minor duplicate scans detected for same `cart_id + ecg_time` combinations

---

### Measurement Quality Issues

#### Logical Sequence Violations
- ~14,716 records violate expected ECG waveform ordering:
  - P-wave onset → P-wave end → QRS onset → QRS end → T-wave end

#### Duration Anomalies
- Small number of negative duration values detected (data inconsistencies)
- Significant cases where:
  - `p_duration > rr_interval`
  - `qrs_duration > rr_interval`

These indicate potential measurement errors.

---

### Data Distribution Insights

- Bandwidth settings are highly standardized (3 dominant configurations)
- Filtering settings are mostly consistent, with majority using 60 Hz notch filter
- Electrical axis values (`p_axis`, `qrs_axis`, `t_axis`) show wide ranges, including extreme outliers

## 5. Data Cleaning Strategy 

The data cleaning process was implemented using Apache Beam as a modular, rule-based pipelines driven by findings from the profiling phase.

For **ECG machine measurements**, cleaning included:
- Removing invalid or missing identifiers and timestamps
- Enforcing ECG physiological ordering constraints (P-wave → QRS → T-wave sequence)
- Filtering negative or unrealistic duration values
- Removing records with inconsistent timing or measurement logic
- Applying multi-level deduplication at study level and machine-time level
- Generating derived features such as `p_duration`, `qrs_duration`, and `qt_proxy`

For **waveform note links**, cleaning included:
- Validating identifiers (`subject_id`, `study_id`)
- Ensuring waveform path structure consistency
- Verifying alignment between `study_id` and file path
- Validating clinical note format (`note_id`)
- Handling optional fields (`note_seq`, `charttime`)
- Deduplicating records per `study_id`

Overall, the cleaning strategy ensures that only clinically valid, consistent, and non-redundant data is passed to downstream transformation and audit stages.

## 6. Transformation & Aggregation Design

This stage builds the final clinical dataset by integrating cleaned ECG measurements with waveform note links and generating machine-level audit metrics.

---

### Data Integration
Cleaned datasets are joined using `study_id` to combine ECG measurements with clinical note information. Records without valid machine measurements are excluded.

---

### Feature Engineering
Clinical rules are applied to detect abnormal ECG behavior based on:
- P-wave, QRS, and QT duration thresholds
- Electrical axis ranges (P, QRS, T)

A final flag is created:
- `scan_abnormal` → indicates if any rule is violated

Each record is also enriched with:
- `has_note` (availability of clinical documentation)
- `note_id` and `waveform_path` when present

---

### Aggregation (Per ECG Machine)
Data is grouped by `cart_id` to compute:
- total scans
- abnormal scans
- abnormal scans without notes
- compliance ratio (abnormal scans with notes)

---

### Audit Output
A detailed dataset is generated for:
- abnormal scans without clinical notes
- full measurement + metadata context

---

### Output
- Machine-level ECG quality and compliance metrics
- Abnormal scan audit table for missing clinical documentation

---

## 7. Pipeline Execution Design

The pipeline is implemented as a modular batch system composed of **multiple independent stages due to local environment limitations** and large dataset size.

### Pipeline Structure

The system is split into the following pipelines:

- **Pipeline 1:** Cleaning ECG machine measurements  
- **Pipeline 2:** Cleaning waveform note links  
- **Pipeline 3:** Join & enrichment of both datasets  
- **Pipeline 4:** Feature engineering, aggregation, and audit generation  

Each pipeline produces intermediate outputs that are consumed by the next stage.
